# How ZT-FedTrust Was Built

This document tells the *story* of building ZT-FedTrust — what was done,
in what order, why each decision was made, what broke along the way, and
how it was verified. For the technical reference (config options, module
map, API), see [README.md](README.md). This file is the narrative behind
it: five build phases plus a sixth phase of presentation work, told in the
order they actually happened.

The project was built as a sequence of five explicit phases, each one
extending the last without rewriting it. Every phase after Phase 3 carried
one non-negotiable rule: **never fabricate a result.** Every number in
this document, and in the project's README and reports, comes from an
actual run against real MNIST data or a hand-computed test case — never
an assumption.

---

## Phase 1 — Baseline Federated Learning

**Goal:** a working, modular FedAvg simulator — nothing fancy, just correct.

The shape decided everything that followed: a `Client` class that owns its
own local model and dataset partition and exposes `train()` /
`get_weights()` / `set_weights()`; a `Server` that owns the round loop
(select clients → broadcast weights → collect local updates → aggregate →
evaluate); and `federated_average`, the plain sample-count-weighted mean of
client updates. Everything is driven by one YAML config, validated on load
so a bad value fails immediately with a clear message instead of failing
deep inside training.

Two real bugs surfaced even at this early stage:

- **MNIST downloads were failing on SSL errors.** The actual certificate
  being served turned out to be generated by the user's antivirus
  software for HTTPS-scanning — not a code bug, a local security-tool
  interaction. Diagnosed by inspecting the served certificate directly
  rather than guessing.
- **Console logging silently produced no output.** `setup_logger()`
  attached handlers to a logger literally named `"simulation"`, but
  `Server`/`Client` logged via `logging.getLogger(__name__)` — a
  different name, so nothing propagated. Fixed by attaching handlers to
  the root logger instead.

By the end of Phase 1: IID and Dirichlet (non-IID) partitioning, MNIST and
CIFAR-10 support, deterministic seeded runs, and a full offline test suite
running against synthetic data (no network access needed for CI).

## Phase 2 — The Zero Trust Engine

**Goal:** before trusting anyone's update, *score* them. This phase adds no
enforcement yet — just measurement.

Five independent dimensions feed one composite score:

```
Trust = w1·Identity + w2·Integrity + w3·Behaviour + w4·Reputation + w5·UpdateQuality
```

The design choice that mattered most here: **Update Quality is computed
from real training signal** — loss improvement versus the client's own
previous round, cosine similarity against that round's mean update
direction, and normalised update magnitude — not simulated. This is the
one dimension that actually reacts to what an attacker does later, in
Phase 4.

The subtler design decision was about **Reputation**. It uses exponential
smoothing (`Reputation_new = α·Reputation_old + (1−α)·CurrentTrust`), but
`CurrentTrust` is computed from the *other four* dimensions, kept
deliberately separate from the final composite score — folding the
composite score into its own reputation update would be circular (a
score updating itself). The same non-circularity concern applies to
*when* in the round `TrustEngine` runs: aggregation for a round always
uses trust as it stood *before* that round's evaluation, never a
client's just-computed score influencing its own weight in the same
round.

Verified with a dedicated regression test
(`test_trust_evaluation_does_not_change_fedavg_result`) proving that
turning trust scoring on produces byte-identical FedAvg output to Phase 1
— scoring with no enforcement should never change training results.

## Phase 3 — Trust-Based Selection and TrustFedAvg

**Goal:** put the scores from Phase 2 to actual use. Two things change:
*who* gets to participate, and *how much* their update counts.

Selection became two explicit stages:

```
All Clients → Threshold Check (TrustPolicy) → Eligible → Participation Sampling (ClientSelector) → Selected
```

`TrustPolicy` owns stage 1. Two threshold strategies were built behind one
interface: `"fixed"` (a constant, e.g. 0.60) and `"adaptive"`
(`mean(trust) − 0.5·stdev(trust)`, recomputed from the current round's
population). `ClientSelector` owns stage 2 — random sampling of
`participation_fraction` of the eligible pool. This separation is why
"Rejected" (failed the trust threshold) and "not selected" (eligible but
not sampled this round) are tracked as genuinely different things, not
conflated.

`TrustFedAvg` extends plain FedAvg's
`Σ(weight·samples) / Σ(samples)` to
`Σ(weight·samples·trust) / Σ(samples·trust)`. Both aggregation strategies
were written to share one calling convention so `Server` never branches
on which is active — only the config string changes. This "strategy
pattern, not an if/else" choice is what made every later phase
(attacks, benchmarking) able to swap aggregation without touching
`Server`.

## Phase 4 — Adversarial Attacks and Security Evaluation

**Goal:** answer, with real experiments, whether the Zero Trust layer
actually does anything against attackers — not just in theory.

Four attack types were implemented, each attacking at a different level:

| Attack | Level | What it does |
|---|---|---|
| Label flipping | dataset | Remaps labels at read time, never mutates the shared underlying dataset object |
| Model poisoning | update | Scales the real update by a bounded factor |
| Byzantine | update | Replaces the update with noise, or its exact negation |
| Sybil | identity | One attacker controlling several registered client IDs |

The single most important design principle of the whole project was
introduced here and never violated afterward:

> **The server, `TrustEngine`, `TrustPolicy`, and `ClientSelector` never
> read `client.is_malicious`.** Ground truth exists only so the
> evaluation code can grade detection *after the fact* — it never flows
> into the defense.

This was enforced structurally, not just by convention: `MaliciousClient`
wraps a benign `Client` via **composition** (a `Client` plus an attack
strategy), exposing the exact same public surface the server already
used. Nothing downstream can distinguish a malicious client from a benign
one without an explicit `isinstance` check — and the only code that ever
performs that check lives in `evaluation/`, strictly for scoring
detection quality, never for making a decision.

A real bug in the *test suite itself* surfaced here: an early Byzantine
trust-degradation test used a 50/50 benign/malicious split, where the
"mean update" baseline was already half-corrupted — masking the very
cosine-similarity signal the test was trying to prove existed. Fixed by
testing against a benign-majority pool (4:1), matching realistic
malicious fractions.

**Honest first result:** at only 2 rounds, reputation's deliberately slow
smoothing (`α = 0.80`) hadn't pushed any malicious client's trust below
threshold yet — detection counts were 0 across all six validation runs.
The trust *gap* between benign and malicious averages was already clearly
visible in the plots, and malicious aggregation weight was already
measurably below a fair sample-count share under TrustFedAvg. The
mechanism was visibly working; it just hadn't had time to act on what it
was observing. That honest, unflattering framing — rather than picking a
config that hides it — became the standard for every result reported
from this point on.

## Phase 5 — Research Benchmarking Framework

**Goal:** turn four ad-hoc phases into a reproducible research tool: run a
real experiment matrix, compute real statistics, generate a real report —
without adding a single line of new FL or trust logic.

This was almost entirely an orchestration exercise. The spec's four
algorithm/attack conditions (FedAvg clean, FedAvg attacked, ZT-FedTrust
clean, ZT-FedTrust attacked) map directly onto the three
`ExperimentRunner` modes Phase 4 already had — condition C is just mode
`ztfedtrust_attack` with `attacks.enabled: false`. `BenchmarkRunner` loops
that mapping across every (algorithm, attack, malicious fraction, seed)
combination and writes one row per round to a master CSV. The only
genuine new source code was per-phase round timing instrumentation
(selection / training / aggregation / trust evaluation), needed for the
overhead metrics.

Two research-integrity rules were built into the framework itself, not
just followed by hand:

- **Failures are recorded, never dropped.** A raising experiment cell is
  caught, logged with `status="FAILED"` and its error message, and the
  sweep continues.
- **Statistical significance is withheld below `MIN_PAIRED_SAMPLES = 3`.**
  The paired significance test returns `None` rather than a p-value when
  there isn't enough repeated-seed data to trust it.

Three bugs were caught and fixed by self-review before results were
considered final: a numpy-bool-vs-Python-bool comparison bug in the
significance test, a zero-variance test case that produced a meaningless
NaN p-value, and an entire statistical-significance report section that
had been implemented but never actually wired into `generate_report()`.

**The validation run** (24 real experiment cells: 2 algorithms × {none,
label_flipping, model_poisoning, byzantine} × 3 seeds, real MNIST, 0
failures) produced the project's first honestly-reported statistical
result: TrustFedAvg cut malicious aggregation weight from 0.25 to 0.077
in every attacked condition — a direct, structural measurement — while
the *accuracy* improvement, though positive in every attacked condition,
did **not** reach statistical significance at only 3 seeds (p ranged
0.17–0.87). The report says this plainly. Overhead was also measured
honestly: 193% higher runtime than plain FedAvg at this small scale —
real cost, reported rather than hidden.

## Phase 6 — Getting It in Front of a Panel

Once the five phases were done, the remaining work was making the project
legible to someone seeing it for the first time: a live demo, an
architecture walkthrough, and defensible answers to hard questions.

### Finding a real bug via `threshold_mode: adaptive`

Building a demo that could show detection *actually happening* (not just
trust scores drifting apart) required `threshold_mode: adaptive`, which
had barely been exercised before — every prior validated result used
`fixed`. The very first real run produced impossible output:
`Eligible: 3, Selected: 7`. Selected can never exceed eligible.

Root cause, found by tracing the code rather than guessing: `TrustPolicy`
computed eligibility once per round, but `is_trusted()` and
`calculate_selection_statistics()` read `client.trust_score` *live* off
the same mutable `Client` objects — and `TrustEngine` mutates that
attribute in place, later in the same round, for whichever clients just
trained. Reading it after that point mixed this round's fresh scores for
some clients with last round's scores for others, all compared against a
threshold computed before either existed. `threshold_mode: fixed` never
exposed this, because a constant threshold isn't timing-sensitive.

The fix: `TrustPolicy` now snapshots every client's score into a
`{client_id: score}` dict at the moment `get_trusted_clients()` runs, and
every later read in the same round consults that frozen snapshot instead
of the live, mutating object. Verified with a new regression test
(`test_eligibility_survives_trust_score_mutation_after_selection`) and a
full suite re-run (163 tests passing) confirming zero regressions
elsewhere.

### Building a demo that actually shows rejection

With the bug fixed, `configs/demo/detection.yaml` (10 clients, 6 rounds,
20% Byzantine "negate" attackers, adaptive threshold) produced a clean
result: both attackers train normally in round 1 (trust ≈ 0.83–0.84),
then the adaptive threshold rises above their score from round 2 onward —
`AggregationWeight = 0.0` for both, every round after. Not scored lower.
Actually excluded. The 3-way `compare_all` run made the contrast
concrete: FedAvg-under-attack never defends (`AttackSuccessRate = 1.0`,
~28.6% malicious weight, every single round); ZT-FedTrust-under-attack
drops both to `0.0` from round 2 on, finishing at 98.5% accuracy — almost
matching the clean, unattacked baseline (98.6%).

The honest caveat, kept rather than hidden: the adaptive threshold
excludes the *bottom* of each round's trust distribution, not a
targeted attacker-only filter — recall hit 1.0 (both attackers caught,
every round) but precision was only 0.5, meaning ~2 innocent clients
were also benched most rounds. A real cost of the mechanism, reported
alongside the win.

### "Isn't the accuracy improvement negligible?"

A fair challenge, asked directly: in the clean demo, 98.5% vs 97.8% is a
small gap. Re-examining the *existing* Phase 5 benchmark data (not new
experiments) surfaced the real answer: FedAvg has no floor. Under
label-flipping, one of FedAvg's three benchmark seeds collapsed to 72.3%
accuracy — an outright failed run — while ZT-FedTrust never dropped below
94.5% on the same attack, same seeds. The honest framing that emerged:
**ZT-FedTrust's value isn't a mean-accuracy improvement, it's a
worst-case reliability guarantee.** On easy conditions FedAvg often gets
lucky enough that its average looks fine; the point of the trust layer is
that it doesn't need luck. A new figure
(`results/figures/figure11_worst_case_reliability.png`) was built
directly from the saved benchmark CSV to make that comparison visible.

## Where things stand

- Full test suite: 163 tests, offline, synthetic data, under a minute.
- Real-MNIST validation runs exist for every phase, with honestly-reported
  results even where they were unflattering (0 detections at short
  horizons, non-significant accuracy deltas, real overhead costs).
- The repository is pushed to GitHub at
  [trefann/ZT-FedTrust](https://github.com/trefann/ZT-FedTrust).
- A ready-to-run panel demo exists in three tiers (fast / larger / trust
  rejection), documented with exact commands, expected output, and
  pre-written honest answers to the hardest likely questions.

The throughline across all six phases: every extension was additive (no
prior phase's code was rewritten to make room for the next), every claim
is traceable to a saved CSV or a specific test, and every unflattering
result was reported rather than smoothed over.
